# 2026-10-19 board A/B: line-major + W64, and the read bypass

All on the board via the serial console (bench_collect.py, board_fps.py), nobody at the keyboard, no sim.
Same system.rv32 (6ada2908, table 1.2) and glass (dfb8afa6) in every run; mode chosen with `glass run --fw-opt=N`.

| Run | Bitstream | --fw-opt | What it is |
|---|---|---|---|
| bench_opt30, fps/old30 | 6261127d (lm8) | 0x30 | old plane-major order, 32-bit row writes = the posted baseline (reproduces 2026-10-18_v6fpu_posted8) |
| bench_lm_default | 6261127d | 0 | line-major groups, no PFB store on the top group |
| bench_w64, fps/lm_w64 | 6261127d | 2 | line-major + 64-bit row writes on HP1 (WRCHAN 0xF00 read back) |
| bench_bypass30, fps/bypass30 | 6b265e6f (read bypass) | 0x30 | old order + ZIGGY read bypass of the posted store buffer |

**CORRECTION (Matt, on screen, 19 Oct evening): W64 drops every odd column** (the upper 32 bits of each
64-bit beat on HP1 are lost — the same symptom as 10-03, so it was not the openXC7 BRAM bug). The W64 runs
(bench_w64, fps/lm_w64) wrote half the data: their numbers are INVALID as a speed-up. Columns come back with
--fw-opt=0 (line-major only). fps/lm_only is the valid line-major run.

**ROOT CAUSE + VALID W64 RUN (2026-10-19 night, decisions.md 2026-10-19):** the AFI, not the RTL. glass
switched HP1 32 -> 64 at run time, after 32-bit traffic; such a channel writes only words 0 and 3 of every
16 bytes. With HP1 0xF00 from boot (prototypes/w64_re/boot_w64.py) W64 is pixel-exact (marker fill on 11
carts, GEM identical to W32). The broken run's TIMINGS stand (it already sent 8-byte beats): the valid
same-boot A/B below reproduces them.

| Run | Bitstream | --fw-opt | HP1 |
|---|---|---|---|
| bench_w64boot, fps/w64boot | 6261127d (lm8) | 2 | 0xF00 from boot |
| bench_w32same, fps/w32same | 6261127d, same boot | 0 | 0xF01 (run-time 64 -> 32, proven correct) |

- fr.dirty.p4 1.133 -> 0.995 Mc, fr.dirty.p2 0.727 -> 0.611, fr.dirty.p1 0.545 -> 0.422.
- fps (w32same -> w64boot): automation442 30.1 -> 60.2, deltaforce 40.3 -> 60.2, stcs 31.3 -> 48.2,
  union_l16 30.3 -> 41.1, ancool 30.1 -> 40.0, fallen_angels 40.3 -> 51.6, union_main 22.1 -> 26.2,
  dbug 25.4 -> 28.2, leonard 59.4 -> 59.4.

Headlines of the first runs (their W64 pixels were wrong, their W64 timings hold, see above):
- fr.dirty.p4 (4 redrawn planes): 3.42 Mc (old) -> 1.13 (line-major) -> 1.00 Mc (+W64).
- fps (lm_w64 vs old30, same bitstream): 29 carts faster, 0 slower (leonard 30->59, automation442 30->60, deltaforce 40->60, stcs 32->48).
- Read bypass: mc.lib.64K 2.74 -> 2.47 c/B (x1.11), mc.word 2.56 -> 2.39; fps: only stcs moved (31.5 -> 36.4), all 103 carts running.

**W64 IS THE DEFAULT (2026-10-19 late, decisions.md "W64 is the board default"):** boot.scr sets HP1 0xF00 and
`glass run` with no flag runs W64. After a plain reboot (prototypes/w64_re/bench_default, fps_default):
fr.dirty.p4 0.996 Mc, p2 0.612, p1 0.423; automation442 60.2, deltaforce 60.2, stcs 48.2, leonard 59.4 fps,
the same as the w64boot run. A board measured from now on is W64 unless `--fw-opt` without bit 1 says otherwise.
