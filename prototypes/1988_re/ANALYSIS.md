# 1988 — how it works, and how the port does it

**1988**, Tristar & Red Sector Inc., C64, *Only Sprites* compo (out of competition), 16 January
2021. Code Shazz, graphics Elko, music Barney Gumble ("Ultimate Intro 12").
CSDb release 198974. Cart `c64_1988` (118), `apps/zig/scenes/c64_1988*`.

## The short answer

- **Only sprites, and only eight.** The screen memory is blank; every pixel is one of the
  VIC-II's eight hardware sprites, reused down the frame by raster IRQs that rewrite their Y,
  X, pointers and colours between uses (multiplexing). Part 1 shows 88 sprite places a frame
  (72 logo + 8 scroller top + 8 bottom), part 3 shows 56 (112 objects: each block holds two).
- **The borders are open where the sprites need them**: top and bottom (RSEL dropped to 24
  rows on line 250, before the bottom compare) for the two scrollers; all four in part 3
  (the same, plus `DEC/INC $D016` around cycle 56 on every line), with the screen itself OFF
  (DEN 0): "runs in IDLE mode".
- **Part 3's bounce is a VIC trick, not motion**: every line, `$D017` is written 0 then a
  mask; a sprite whose bit is set repeats its row on that line (the Y-expansion flip-flop
  never lets MCBASE advance). Each column clears its bit for the 20 lines its bounce table
  gives, so the object sits lower or higher inside a fixed 37-line band.
- **Precalculated everything**: the code was generated by Shazz's Python cross-assembler
  (shazzam), so the logic is unrolled and every coordinate comes from a table: X tables with
  the PAL wrap folded in ("X coordinates precalculated"), sines for the logo, bounce tables,
  wipe lines. The multiplexer's rows are timed so no sprite's DMA restarts in the wrong place
  ("sprite movement restricted to avoid the sprite-DMA bug").

## The parts

The main loop (`$1E00`) runs the three parts forever; each part's IRQ chain raises `$1FFE`
when it is done, the main loop clears the frame counter (`$1FFC/$1FFD`), calls play once more
and starts the next part (each init waits for line 256 then line 0). Frame numbers are VICE's
raster frames from the `$1E00` entry (frame N ends when the beam reaches line 288).

| Part | Entry | Frames | On screen |
|---|---|---|---|
| 1 | `$5300` | 3..1645 (1643) | Elko's skull logo, 8 x 9 multicolour sprites, bobbing on two sines; the same proportional scroller (8 X-expanded hires sprites) in the top border and the bottom border; after 1600 frames the logo fades (6 steps of 7 frames). Texts 1, 2, 3 in turn, one a loop |
| 2 | `$E200` | 1646..1715 (70) | screen off, the border goes blue from the top, 4 lines a frame |
| 3 | `$4000` | 1716..2183 (468) | 8 columns of cubes (the first time) or balls (the next), 7 bands down the open screen; columns join from the right every 18 frames, the grid scrolls 3 px a frame and animates every 2nd frame; after 300 frames the colours fade (9 steps of 10 frames) |

Loop: 2183 frames (43.7 s at 50 Hz). Texts x variants: the whole show repeats after 6 loops.

## Part 1 ($5300): the multiplexed logo and the border scrollers

IRQ chain, one frame:

| Line | Handler | Writes |
|---|---|---|
| 0 | `$5500` | the 8 Y to `$10` (the top scroller; X, pointers, colours are still the bottom one's from line 250), then the scroller steps; `$D011` RSEL back on |
| 36/37 | `$56BC/$56DE` (stable) | X-expand off, multicolour on; frame counter: < 1600 colours `$0B/$0F/$0C`, = 1600 the fade, after the fade the end; then the logo: Y = `$6065[i]`, X = `$6001[j]` + 24 per column (+ MSB), row 0's pointers |
| base+17+20(k-1) | rows k = 1..8 | Y = base + 21k, pointers 8k..8k+7 (`SAX` gives `A & X` = 0..3, `STX` 4..7) |
| base+177 | `$5D0C` | pointers 0, Y `$0A` (line 266: the bottom scroller), X-expand on, multicolour off |
| 250 | `$5D9F` | RSEL off (the bottom border never closes, so the top stays open too), white, the scroller's pointers, X (`$6397[idx]`, MSB `$63FC[idx]`), play `$1003` |

**Row timing.** A row's IRQ lands its writes 2 or 3 lines later depending on where the bad
lines fall (the screen is on in part 1): by the IRQ line's phase (line & 7) the Y writes are
at +3 +2 +2 +2 +2 +2 +3 +3 and the pointer writes at +4 +3 +3 +3 +3 +4 +4 +4 (measured over
two loops of traces, never different). So row k's pointers change while row k-1 still shows
its last lines: those lines already show row k's blocks. Elko's logo is cut for it.

**The scroller** (`$5500`, 8 unrolled blocks, sprite 7 down to 0): each sprite has a position
index (`$40-$47`) into the X table, 4 px a step (X-expanded sprites, 48 px wide). An index
reaching 0 (off the left edge) is recycled behind the previous sprite of the ring with the
next character: index = previous + 12 - `$6358[char]` (the per-glyph cut: proportional
spacing), pointer = char + `$48`. Sprite 0 follows a sprite 7 already moved this frame: +13.
The text is copied to `$60A2` from index 1 to its length (index 0 is never copied) and read up
to index 250 (wrap `$F3`). Text 3's byte 145 is the length table's own first byte, 145: once a
loop the scroller shows sprite block 217 (`$F640`), i.e. VICE's power-on RAM pattern
(stripes). The port shows them too (bank 3 is ripped from VICE's RAM at `$1E00`).

**Tables**, all regenerated at comptime (`tables.zig`) and tested against the ripped bytes
(`tables_test.zig`): logo X `round(80 + 40 sin(2 pi i / 50))` (100 bytes), logo Y
`round(53 + 7 sin(2 pi i / 20))` (40), scroller X `4i - 25`, negative + 504, + MSB (101).
Ripped (data, not formulas): the three texts (ASCII - 32), the glyph cuts, the fade.

## Part 2 ($E200): the wipe

Screen off (`$D011 = $08`): with DEN 0 the vertical border flip-flop is never reset on line 51,
so the border covers the whole screen, and every sprite (part 1's are still enabled). Line 0:
`$D020/$D021` blue. Frame k: a stable double IRQ on line `12 + 4k` (table `$E359/$E39F`,
regenerated) sets them black two lines later. On the lines where the scrollers' sprites are
still fetched (their DMA runs on under the closed border) the store lands at cycles 33-52
instead of 10, so on the wipe's first 6 and last 5 frames the switch happens mid-line (first
black pixel at VICE column 8 x cycle - 103; VICE's 8565 paints a light-grey "grey dot" pixel
just before it).

## Part 3 ($4000): bouncing objects in the open border

IRQ chain: line 22 (`$4400`, stable: sprites on), then **one loop per line for 35 lines, six
times** (bands at lines 24 + 37b, Y `$18 $3D $62 $87 $AC $D1`), each band followed by the next
band's Y; line 247 (`$4662`, stable): `$D011 = $00` (RSEL off: the vertical border stays open
with the screen off), the 7th band (lines 249..283, Y `$F9`), then the end handler. The loop:

```
STY $D017        ; 0: every flip-flop held set
LDA $6C,X        ; this line's mask
STA $D017        ; masked sprites: the flip-flop toggles to 0 at c55, the row repeats
LDA $4CBE,X      ; (timing filler)
BIT $EA / NOP NOP
DEC $D016        ; 38 columns at cycle 56: between the X=335 and X=344 compares
NOP NOP
INC $D016        ; back to 40 columns
```

The body is 46 cycles; the sprite DMA takes most of the rest of the 63. After each band's Y
rewrite the loop starts early and catches up 2 cycles a line (the DMA stalls synchronise it):
the DEC lands at cycles 48/50/52/54 on the band's first four lines, before the X=335 compare,
so **those lines' right border closes** (and the next line's left). The bottom band's 4th line
lands at 54 or 55 from the IRQ's jitter (2 frames in 3 at 54, chaotically, differently on
each loop).

End handler (line 284, runs on to line ~13 of the next frame): sprites off; scroll step `$60`
17..0 (X from `$51CF + 18c + step`, MSB `$525F`: the first frame reads index 18, one past each
column's table, and for column 7 the MSB table's first byte, then `$52EF`); pointers from the
animation table (`$4C7E`: 10 or 13 frames twice + a blank); every 2nd frame the animation
advances and columns `$6B..7` take it (`$6B` counts 7 down to 0, one every 18 frames: the
columns join from the right); masks: all `$FF` (`$4B6F`), then each column clears its bit in
20 masks from `bounce[step + 18c]` (`$480E`, 8 x 20 `SAX`; `$4CBF` holds a copy of variant A's
`$4E6F` or B's `$501F`); play; the join counter; from frame 300 the fade (every 10 frames,
`$4C9D`: `$D025/$D026/$D027`, border). The join and the fade share one counter (`$4C9A`),
which then runs past 255; the last fade step reads one past the border table: `$4CBD`
itself, 8 (orange).

Tables: X `54c + 3s - 24`, negative + 503 (one less than part 1's wrap: kept, it is the
original), MSB; balls `round(14 |sin(pi n / 24)|)` (216); cubes `$4E6F` (216 bytes): no simple
formula reproduces it (the best sine fit matches 196 of 216), so it ships as ripped data.

## Music

Ultimate Intro 12, Barney Gumble, 2020 (released "2020 Ultimate"). PSID v2, load `$1000`,
init `$1000`, play `$1003`, 1 song, PAL, 8580 (flags `$24`). Played once a frame from each
part's last IRQ (part 1 line 250, part 2 after the black store, part 3 the end handler), plus
once more by the main loop at each part change. HVSC `/DEMOS/S-Z/Ultimate_Intro_12.sid`,
byte-identical to the copy in the PRG. Licence: as the ST ports ship SNDH files from the
archive, the port ships the HVSC file.

**Not wired yet**: the SID player (cRSID on BARD, `PLAYER_SID`) is on branch `feat/sid-bard`,
not on main. `MUSIC_SID` in `apps/zig/scenes/c64_1988.zig` is the one switch (off); the
ROADMAP row "1988 music" holds the steps. The 3 extra play calls a loop (part changes) are a
60 ms drift a loop that a 50 Hz player will not reproduce.

## The port

**One idea: keep the C64's model.** `vic.zig` + `vic_draw.zig` are the VIC-II's sprite unit
(C. Bauer, "The MOS 6567/6569 video controller", 3.8/3.9): MCBASE/MC, the Y-expansion
flip-flop at c15/16, c55, c58, DMA start at the Y match, the fetch at c58 shown on the next
line, the vertical border flip-flop (RSEL, DEN), the side border (a `$D016` DEC at cycles
55..56), a border colour change mid-line. Each part (`logo.zig` + `scroll.zig` +
`logo_rows.zig`, `wipe.zig`, `grid.zig` + `grid_bands.zig`) emits the register writes its IRQ
chain makes, at the original's raster lines and cycles; `show.zig` is the main loop and the
parts' init frames. Nothing is "drawn to look like" the effect: the multiplexing, the stretch
and the open borders come out of the rules. No float per frame (the tables are comptime).

On the machine:
- one 400x280 overscan plane: physical row = raster line - 11, column = sprite X + 16, so the
  C64's 320x200 window is the machine's. Each sprite row is a keyed CPU blit of 24 (48)
  pixels (CHISEL's ~800-cycle fixed cost is more than a row); only rows drawn last frame are
  erased;
- the machine's borders open where the C64's are: the plane's HBL flickers the band rows when
  the C64's vertical border is open and the visible rows whose side border is open; pixels
  the C64's border covers are not drawn, so a line with only its left border open is exact;
- the border colour is a real raster, like colour 0 on an ST: per line BACKGROUND (global HBL,
  the closed borders) and the plane's colour 0 (plane HBL, the window and the open borders),
  plus BEAM for part 2's mid-line switch to black;
- 50 Hz on the 60 Hz machine: C64 frame n on machine frame ceil(6n/5).

Palette: **colodore** (VICE's `colodore.vpl`), the 16 entries exactly; VICE captured with the
neutral colour pipeline (gamma 1000 etc.) so its pixels are those entries.

### How exact (measured)

- **The sprite model vs VICE 3.9 x64sc**: `tools/c64/vicmodel.py` (Python) and then `vic.zig`
  fed the original's own write stream (VICE trace) agree with **192 of 204** VICE captures
  pixel for pixel over two loops. The others: 10 frames by ONE pixel (VICE's 8565 grey dot at
  part 2's mid-line switch: the port shows the new colour there), frame 2 (the boot frame:
  BASIC's text), frame 1773 (2 pixels at a band start in part 3's first frames: not
  understood).
- **The port's logic vs the original's**: `tools/c64/scene_dump.zig` + `replay --diff` run both
  write streams through the same sprite unit, every frame of two loops: **4388 of 4400 frames
  identical**. The 12 others are the original's IRQ jitter, which differs run to run: the
  bottom band's 4th line (the port keeps its right border closed, the 2-in-3 case) and the
  wipe's stable-raster landing cycle on 4 border lines in the second loop (the port uses the
  first loop's).
- **The cart through the machine**: `apps/c64_1988_headless.mjs` pins 9 frames across two
  loops to VICE's SHA-256 (`compare/`).

### Cost on KESTREL

`apps/frame_cost.mjs`: est. **1.88 Mc a frame** in part 1 and part 3 alike (cart 1.18, FRESCO 0.7
for the one plane), ~53 fps; the C64's 50 Hz means one machine frame in six steps nothing.
What made it: a sprite row drawn a data byte at a time (empty bytes skipped, no clipping inside
the window), no per-frame copy or sort of the write list (the parts emit in line order; the
unit panics on a write out of order rather than drop it). Board check wanted.

### What KESTREL could lift

The C64 needed the per-line loop to keep the side borders open and to stretch the sprites;
the port pays nothing for either (a flag per row, a row index per line). A ZIG mode could keep
the look and add what the VIC could not: more than 8 objects a line without multiplexing, the
logo's rows without the pointer-switch lines, 60 Hz motion.
